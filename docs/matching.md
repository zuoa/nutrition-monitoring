# 消费图片分轮匹配

在「系统设置 → 业务规则 → 消费匹配轮次」中增删轮次并保存。默认 `1、3、5` 是三轮，分别扫描校正后时间的 ±1、±3、±5 秒；每项为 1～86400 的整数，且必须严格递增。环境变量 `TIME_MATCH_WINDOW_STAGES=1,3,5` 作为启动默认值，设置页保存的运行时配置优先。

同一消费日期的全部流水完成一轮候选收集后，才会分配图片。该轮按绝对时差、流水 ID、图片 ID 排序，一对一分配；已分配结果保留，剩余流水进入下一轮。金额必须完全一致，通道和有效图片筛选继续生效。超出最后一轮仍保持未匹配。

消费导入和图片识别完成都会触发涉及日期的统一重算。重复请求会合并；单图入口也会提交日期任务，结果完成后刷新查看。日期重算会重新分配旧自动匹配，保留人工匹配、已确认结果及其占用图片；其他日期已经占用的图片也不会重复分配。跨日期之间不进行全局最优重排。

匹配详情区分原始绝对时差与校正后绝对时差，并记录实际应用的校正值、命中轮次和窗口。例如消费时间加 10 秒进行校正，原始时差 11 秒时，校正后可能只有 1 秒。校正优先采用消费发生时的校时样本，再使用最近样本；没有样本时使用手工配置。历史结果缺少诊断字段时显示“未记录”，重新匹配后补齐，不使用当前校正值反推历史结果。

## 后台运行与恢复

`matching_runs` 每个日期保存一条运行状态，阶段为 `idle → collect → allocate → publish → notify`。`matching_candidates` 暂存当前轮候选。候选收集与分配按 `MATCHING_BATCH_CHUNK_SIZE`（默认 200）分片，主动时间预算由 `MATCHING_BATCH_TIME_BUDGET_SECONDS`（默认 240）控制。

每次运行冻结有效配置、校正值和输入数据，前台继续看到上一版匹配结果。发布前重新检查消费、图片、金额及人工确认等输入；发生变化时丢弃草稿并重算。发布在单个数据库事务中完成，随后为受影响学生重新计算营养日志，包括失去自动匹配的学生。营养任务通知可重试，可能重复投递，但计算应保持幂等。

PostgreSQL 使用日期任务行锁串行推进，同一日期的重复任务安全续跑。发布时短暂锁定相关业务表，防止识别修改或人工确认与验证、替换之间发生竞争；不同日期发布也会串行，避免跨午夜重复占图。完整输入快照和最终发布仍按日期进行，超大日期的数据量会影响内存与发布耗时，需要观察运行日志。

Celery Beat 每分钟调用 `recover_matching_runs`，恢复未完成日期，覆盖提交后派发失败和任务中断。运行时配置文件须在 API 与 matching worker 间共享；发布日志包含日期、代次和自动配对数量。

## 升级与验证

先停止旧版本 matching worker，应用迁移 `20260914_0026`（常规部署使用 `make migrate`），再启动新 API、matching worker 和 Beat。迁移新增两张任务表及三个可空匹配诊断字段，不自动重新匹配历史数据。旧批次任务的续跑参数继续兼容，但会转为按日期调度。部署完成后，可使用现有“重新匹配”入口更新需要修复的历史日期。

验证命令：

```sh
cd backend
python -m pytest tests/test_matching.py tests/test_time_calibration.py tests/test_matching_migration.py -q
# 显式指定测试 PostgreSQL；用随机 schema 隔离并自动删除测试数据。
MATCHING_TEST_DATABASE_URL=postgresql://user@localhost/testdb python -m pytest tests/test_matching_postgres.py -q
```

前端执行 `npm run build`，并检查轮次增删、递增校验、保存及匹配详情的两种时差显示。
